# 11 · 🅑-1b 车厢空间索引：算法原型实测（候选集 −98.8%，11–14×）

## 11.1 问题

`Train#findCollidingTrain` 每 tick 对**每一列车**都要遍历**其它列车的每一节车厢**：

```
per tick:  T 次查询 × (T-1) 列车 × C 车厢 = O(T²·C) 次远近判断
per query: T×C 次
```

上一轮（🅑-1）把**每次 `getPosition` 的成本**降了 6–13 倍，但**比较次数没变**。这一步解决次数。

## 11.2 关键前提：原版自己已经给了"半径"

原版循环体里有一句：

```java
if (Math.min(start2.distanceToSqr(start), end2.distanceToSqr(start)) > maxDistanceSqr)
    continue Trains;
```

`maxDistanceSqr = maxAssemblyLength²`。也就是说：**任何车厢的两个端点都超出这个半径的列车，原版本来就会被整列跳过**。
因此"只用半径内的车厢做候选"与原版**结果相同**（不是近似，是同一判定）。

## 11.3 原型实现

新增 `com.tkisor.fettle.alg.SpatialBuckets`：以**查询半径作为格子边长**的均匀网格。

- 查询时遍历"查询球包围盒"覆盖的所有格子，再对格子内每个点做**精确平方距离**过滤 → **保守**，不会漏候选；
- 网格与点数组分离，重建一次 O(P)，查询不开辟新结构（格子内容是 `int[]`）。

## 11.4 实测（`/fettle micro collisionFilter`，60 轮取最优，含 10 轮预热）

场景：**200 列车 × 4 车厢 = 800 个位置点**，列车沿 x 轴每 40 格一列（模拟铁路线），查询半径 32 格。

| 指标 | 朴素（原版形态） | 网格索引 | 变化 |
| --- | --- | --- | --- |
| **实际做距离判断的点数**（确定性指标） | **160,000** | **1,999** | **−98.8%** |
| 耗时 | 342.9 / 343.9 µs | **31.1 / 25.1 µs** | **11.0× / 13.7×** |
| 命中数（正确性对照） | 999 | 999 | **一致 ✅** |

> 两次独立运行的确定性指标完全相同（160000 → 1999），命中数完全相同 —— 这是"算法没改语义、只改工作量"的证据。

## 11.5 接入 `Train#findCollidingTrain` 的设计与唯一风险点

接入方式：在 `findCollidingTrain` 头部建/取本 tick 的网格，用它筛出**候选列车集合**，然后对这些列车跑**原版的内层循环原样**（`lastPoint`/`betweenBits`/`intersect` 全部不变）。

- **唯一需要决定的点**：原版每次查询都重新读 `getPosition`（同一 tick 内若有列车移动，它读到的是新值）。网格是一份**快照**，若同一 tick 内其它列车移动，快照可能偏旧 → 理论上可能漏掉"刚好在这一 tick 移动进半径"的列车。
- **方案 A（推荐，保持精确）**：使用快照前，对每列车做一次**廉价签名校验**（只读 `(edge, position)` 字段，不调用 `getPosition`）。签名不符 → 就地重建该列车的格子条目。代价是每查询 O(T) 次字段读，相对原来 O(T×C) 次 `getPosition` 仍然小两个数量级。
- **方案 B（激进，允许极小偏差）**：同 tick 内直接用快照，跨 tick 失效。收益比 A 略高，但需要你确认接受"同 tick 内移动中的列车可能被漏检一次"。

结合已有成果，完整形态是：**位置计算成本 ÷6–13（🅑-1） × 候选数 ÷80（🅑-1b）**。
