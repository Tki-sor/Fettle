# 08 · 激进路线第一步：预编译位图索引（🅐）

按你的授权开始做"不局限于常规优化"的路线。第一步是把配方索引从**哈希集合**换成**预编译位图数据平面**。

## 8.1 做了什么

旧实现（第二轮，−28%）：`Map<Item, Set<RecipeHolder>>` + 每次查找做 HashSet 并集。
新实现：

1. **reload 时构建期预编译**：为每个 `RecipeType` 的所有配方分配 `0..n-1` 的稠密下标（顺序 = 原版 `byType` 顺序）；
2. **物品 → 稠密 slice**：只对配方里出现过的物品建一次 `IdentityHashMap<Item,Integer>`；
3. **一块扁平 `long[]` arena**：物品 slice × 位图 = 该物品能匹配的配方位集合；整个结构是**纯原生数组，查找零分配**；
4. **查找 = 按位或**：把输入的每个槽位对应 slice 与"不可索引配方"的 slice 一起 OR 进**线程本地 scratch 位图**，然后**按位升序**遍历——这正好等于原版遍历顺序，所以第一个通过 `matches()` 的配方与原版返回的完全相同。

语义保证没变：**位图只决定"问哪些配方"，最终判定仍是原版 `Recipe#matches`**。

## 8.2 实测（同 JVM 微基准，交替 2 组）

`/fettle micro getRecipeFor 200000`，256 个由真实配方构造的合成输入：

| 模式 | ns/op | 相对原版 |
| --- | --- | --- |
| **位图索引 on** | **3501 / 4133** | **−85%**（6.3–7.7× faster） |
| 位图索引 off（等价于线性扫描） | 27018 / 25541 | — |
| （对照）原版纯扫描 | 23 377–25 248 | 基线 |
| （对照）第二轮 HashSet 索引 | 16 979–18 756 | −28% |

→ 从"每次查找省 6.5 µs"变成"**每次查找省 ~20 µs**"。**相对上一版索引又快了 ~4.5 倍。**

**正确性门禁**：`/fettle selftest` → `checked=1211 skipped=340 **mismatches=0**` ✅（对 1211 条真实 crafting 配方逐条与原版暴力扫描比对，零偏差）

## 8.3 顺带给出的"更激进"清单（按可执行性）

| 方向 | 说明 | 预期 | 风险 | 状态 |
| --- | --- | --- | --- | --- |
| 🅐 预编译数据平面 | 稠密 id + 位图 + 每机器子集 | 已实测 **6–7×** | 低 | **已落地** |
| 🅑 换算法 | 列车碰撞 → 一维区间索引（O(T²·C) → O(T log T)）；动力学网络 → 增量生成树 | 大基地 **2–10×** | 中高 | 待做 |

## 8.4 下一步（按顺序）

1. **🅑-1 列车碰撞一维区间索引**：把 `Train.findCollidingTrain` 的 O(T²·C) 全对比较换成"每图沿轨道弧长排序 + 扫描线"，这是大铁路网最明显的算法级收益；
